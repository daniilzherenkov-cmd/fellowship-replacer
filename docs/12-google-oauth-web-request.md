# 12 - Google Calendar access request (web app)

What is needed to turn on Google Calendar in Fellow 2, now that the app is a web
app rather than a native Mac app. Written to be forwarded as-is.

## The short version

The RFC (docs/09 §3.1) asked for an **iOS-type** OAuth client, because at the
time Fellow 2 was a macOS app. **That credential does not work for a web app.**
The ask below replaces item 4 of §3.1; everything else in §3.1 still stands.

| | RFC asked for (macOS) | Now needed (web) |
|---|---|---|
| Client type | iOS | **Web application** |
| Identified by | Bundle id `com.deliveryhero.fellow2` | **Redirect URI** |
| Client secret | None (public client) | **Yes** |
| Redirect | Reversed-client-id URL scheme | `https://<host>/api/auth/google/callback` |

Everything else is unchanged: same project, same Internal consent screen, same
read-only scope, same $0 cost.

## What to create

1. **Google Cloud project in the DH org** (as per RFC §3.1 item 1).
2. **Enable the Google Calendar API.**
3. **OAuth consent screen: Internal.** Internal means only DH Google accounts
   can use it, with no Google app-verification and no "unverified app" warning.
4. **Create credentials → OAuth client ID → Application type: `Web application`.**
   - Name: `Fellow 2 (web)`
   - **Authorised redirect URI:** `https://<subdomain>.dhapps.ai/api/auth/google/callback`
     - Exact-match, so the final subdomain must be known first. Add a second
       entry for `http://localhost:3000/api/auth/google/callback` if local
       development against real Google is wanted.
   - Authorised JavaScript origins: not required (no browser-side Google calls).

## What to send back

Three values, which go into the app as secrets (never into the repo):

```
GOOGLE_CLIENT_ID       = <...>.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET   = GOCSPX-<...>
GOOGLE_REDIRECT_URI    = https://<subdomain>.dhapps.ai/api/auth/google/callback
```

Stored via Protoship's `add_secret`, which writes to HashiCorp Vault and injects
them as environment variables at container start. They are read server-side only
and cannot reach the browser bundle: the Vite/Next build happens in Docker long
before Vault is contacted, so build-time inlining cannot pick them up.

## Scope requested

**`https://www.googleapis.com/auth/calendar.readonly` only.**

Read-only is deliberate. Nothing in v1 creates or edits calendar events, and the
write scope (`calendar.events`) triggers a heavier Workspace-admin review. If
event creation is wanted later, that is a separate, narrower conversation.

## Why the app needs it

Fellow 2 reads the user's own calendar to list their meetings and attach notes
to them. Each user authorises their own account through the standard Google
consent screen; the app never accesses a calendar the user has not connected.
There is no service account and no domain-wide delegation, so no ability to read
anyone's calendar without their explicit consent.

## Security posture

Already implemented and tested (58 tests):

- **Authorization code + PKCE.** PKCE is not strictly required for a
  confidential client but costs nothing and closes code interception.
- **Refresh tokens encrypted at rest** (AES-256-GCM, key from Vault). Access
  tokens are never persisted, only minted on demand.
- **CSRF-protected callback.** Single-use `state` row, plus a check that the
  identity finishing the handshake matches the one that started it - so a code
  obtained in one session cannot be redeemed into another user's account.
- **Per-user authorization on every query.** Protoship admits any DH Okta
  account to the app, so the app verifies the signed Cloudflare Access JWT (not
  the spoofable plain email header) and scopes every row to that identity.
- **Disconnect revokes at Google**, not just locally, so removing the connection
  actually ends access.

## One additional secret needed

Independent of Google, and required before any credential can be stored:

```
FELLOW_ENCRYPTION_KEY = <32+ random characters>
```

This encrypts stored refresh tokens. It can be generated by us; it is listed
here only so it is not forgotten. The app refuses to store credentials without
it rather than falling back to a default key.

## Status without this

The full OAuth flow is built and merged. Until the three values exist,
`/api/auth/google/start` returns a clear `google_not_configured` message and the
UI shows Google Calendar as unavailable. **No other functionality is blocked** -
meetings can be created manually, and a Fellow JSON export can be imported for
history.
